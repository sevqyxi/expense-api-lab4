# Лабораторна робота №4

**Дисципліна:** Технології розроблення серверних компонентів

**Тема:** Аутентифікація (JWT), рольова модель контролю доступу (RBAC) та автоматизоване тестування у CI.

## Опис роботи

У цій лабораторній роботі доопрацьовано REST API для обліку витрат із ЛР3.

Додано реєстрацію та вхід користувачів, захист паролів алгоритмом Argon2id, аутентифікацію через JWT і три ролі користувачів. Також написано автотести на Pytest, які запускаються в GitHub Actions разом із PostgreSQL.

Використані технології:
- Python + FastAPI
- PostgreSQL 16 (Docker Compose)
- SQLAlchemy, Alembic, Pydantic
- PyJWT — JWT-токени
- cryptography (Argon2id) — хешування паролів
- Pytest, pytest-freezer — автотести
- GitHub Actions — CI
- Bruno — ручне тестування API (формат OpenCollection YAML)

Логіка варіанта 2 з ЛР3 (`V = (4606 % 3) + 1 = 2`, персональні та глобальні категорії) збережена.

## JWT і ролі

`POST /register` створює користувача. Пароль зберігається тільки як хеш Argon2id, а нова реєстрація завжди отримує роль `user`.

`POST /login` перевіряє логін і пароль та повертає Access JWT. У токені є id користувача (`sub`), роль (`roles`) і термін дії (`exp`). Токен передається в заголовку:

```
Authorization: Bearer <access_token>
```

Без токена, з неправильним або простроченим токеном сервер повертає `401`. Поточний користувач визначається тільки за токеном, тому підставити чужий `user_id` у запит не вийде.

Ролі:
- `user` — працює тільки зі своїми даними: профіль, свої витрати, свої персональні категорії, перегляд глобальних категорій. Чужі дані — `404`, адміністративні маршрути — `403`.
- `auditor` — тільки читання: список і профілі всіх користувачів, витрати та категорії будь-кого. Будь-який запис — `403`.
- `admin` — повний доступ: видалення користувачів, зміна ролей, глобальні категорії, будь-які витрати.

Нові та змінені маршрути:
- `POST /register`, `POST /login` — публічні;
- `GET /healthz/live`, `GET /healthz/ready` — публічні, перевірка стану сервісу і БД;
- `PATCH /user/{user_id}/role` — зміна ролі (тільки admin);
- `POST /category/global` — створення глобальної категорії (тільки admin);
- `POST /category` — створення персональної категорії;
- `POST /user` з ЛР3 прибрано, замість нього `POST /register`.

## Запуск проєкту

Потрібні Python 3 та Docker Desktop.

Створюємо файл налаштувань (порт БД, секрет JWT):

```bash
cp .env.example .env
```

У `.env.example` вже вказано порт `5433`. Якщо у вас вільний 5432, можна змінити `POSTGRES_PORT=5432`.

Запускаємо базу даних:

```bash
docker compose up -d
```

Створюємо віртуальне середовище та встановлюємо залежності:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Запускаємо сервер:

```bash
uvicorn main:app --reload
```

Документація API: http://127.0.0.1:8000/docs

## Міграції

Міграції Alembic застосовуються автоматично під час запуску застосунку. Вручну:

```bash
alembic upgrade head
```

Нова міграція `0003_add_auth_fields.py` додає до таблиці `users` поля `username`, `password_hash` і `role`. Міграції ЛР3 (`0001`, `0002`) не змінювались.

Старі користувачі з ЛР3 не мають логіна й пароля. Після міграції вони отримують роль `user`, їхні витрати й категорії зберігаються, але увійти вони не можуть. Admin бачить таких користувачів у `GET /users` і може їх видалити.

## Тестові користувачі з ролями

Через `/register` можна отримати тільки роль `user`. Admin створюється командою:

```bash
python create_user.py admin Admin12345 --role admin
```

Auditor створюється так само (`--role auditor`) або admin змінює роль через `PATCH /user/{user_id}/role`.

## Тестування через Bruno

1. Запустити БД і сервер, створити admin командою вище.
2. Відкрити папку `bruno_collection` через Open Collection.
3. Вибрати середовище `Local`.
4. Запустити всю колекцію через Runner.

Колекція містить 61 запит: healthcheck, реєстрацію, вхід, запити від user, auditor і admin, перевірки `400`, `401`, `403`, `404`. Після логіну токени автоматично зберігаються у змінні `userToken`, `otherToken`, `auditorToken`, `adminToken` і підставляються в наступні запити. Логіни генеруються для кожного запуску, а в кінці створені дані видаляються, тому колекцію можна запускати повторно.

## Автотести (Pytest)

Тести запускаються при запущеній БД однією командою:

```bash
pytest
```

Тести працюють з окремою БД `expenses_test` (створюється автоматично), основна БД `expenses` не змінюється. Перед кожним тестом таблиці тестової БД очищаються.

- `tests/test_security.py` — модульні тести: Argon2id, JWT, валідація;
- `tests/test_auth.py` — реєстрація, вхід, токени, `401`, healthcheck (зокрема з заморозкою часу);
- `tests/test_rbac.py` — ролі user, auditor, admin, категорії, `403`, `404`;
- `tests/test_migrations.py` — міграція старих користувачів з ЛР3.

## GitHub Actions

Файл `.github/workflows/ci.yml`. При кожному push і pull request GitHub Actions на Ubuntu:
1. піднімає PostgreSQL 16 як service container;
2. встановлює Python і залежності;
3. застосовує міграції Alembic до тестової БД;
4. запускає всі тести Pytest.

Результат видно на вкладці **Actions** репозиторію. Для CI використовуються окремі тестові значення пароля БД і секрету JWT. Файл `.env` у репозиторій не потрапляє.
